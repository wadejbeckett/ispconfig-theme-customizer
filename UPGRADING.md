# Upgrading

Two different upgrades are covered here, and they have almost nothing to do with each other:

- **ISPConfig upgrades.** The panel moves; the extension has to be re-stamped against it. This is the section that matters, and it applies to *every* ISPConfig release including patch releases.
- **Upgrades of this extension.** Pull a new tag and re-run the installer.

Nothing this extension installs modifies an ISPConfig core file, so a panel upgrade does not undo it the way it would undo a patched core file. What *is* affected is one small piece of metadata the panel uses to decide whether a third-party theme is allowed to load. Both designs need the version re-stamp, and one `install.sh` run does that for both; only clarity has template contracts to check by hand, because classic's shell is regenerated by that same run.

## What survives an ISPConfig upgrade

**The branding data survives.** Everything the Branding page manages lives in ISPConfig's own storage: the `[branding]` section it adds to the `sys_ini.config` blob, the stock `[misc]` keys of *System → Interface Config*, and the native `sys_ini.custom_logo` column. It adds no tables and no columns. An upgrade migrates that row rather than resetting it.

**The deployed directories normally survive.** The ISPConfig updater installs the interface by overlaying its own tree onto yours — `cp -rf ../interface $install_dir` in `install/lib/installer_base.lib.php`. It is a copy, not a sync, so paths that exist only in your install are not touched. The updater's separate cleanup routine deletes an explicit, hardcoded list of obsolete *core* paths and nothing else; none of `themes/clarity`, `themes/classic` or `interface/web/customizer` is on it.

**`$conf['theme']` survives, if you set it in both files.** The updater reads the old configuration from `server/lib/config.inc.php` (`install/update.php`) and carries `$conf['theme']` forward from there. Set it only in `interface/lib/config.inc.php` and the value is lost at the next upgrade, silently: the login screen reverts to the stock theme with no error. Setting it in both files is a documented manual step; `install.sh` never edits ISPConfig configuration.

## What you must redo after an ISPConfig upgrade

Re-run the installer after **any** ISPConfig upgrade, including a patch release such as 3.3.1p1 to 3.3.1p2:

```bash
cd /opt/ispconfig-theme-customizer      # your clone
git fetch --tags && git checkout <tag>  # only if you also want newer code
sudo ./install.sh                       # re-stamps the version gate
```

That single run covers both designs: it re-stamps the version gate for every design it installs, and regenerates classic's shell from the new stock templates. Re-run it **with the flags you originally installed with**, because both flags that change what a run means default to the narrow case:

- If the original install used `--copy`, pass `--copy` again. The installer removes whatever is at the destination and redeploys in the mode you ask for, so a bare re-run would convert a copied install into a symlink pointing at the clone.
- If you installed anything other than clarity, pass `--design` again. With no `--design`, `install.sh` means `clarity`. On a panel running classic, a bare re-run deploys and stamps clarity and never touches `themes/classic`, which is left holding the previous panel's version stamp and a shell generated from the previous panel's templates.

### Why the re-stamp is needed

ISPConfig gates third-party themes on an **exact string match** against `ISPC_APP_VERSION`, which changes on every release, patch releases included. Eight places in core read it, under two different filenames:

| Core file | Reads | What a mismatch does there |
|---|---|---|
| `web/login/index.php` | `ispconfig_version` | at login, forces the session theme to `default` and raises `theme_not_compatible` |
| `web/tools/user_settings.php` | `ispconfig_version` | the save handler behind *Design*: silently rewrites the submitted theme to `default` |
| `web/tools/form/user_settings.tform.php` | `ispconfig_version` | drops the theme from *Tools → User Settings → Design* |
| `web/admin/form/users.tform.php` | `ispconfig_version` | drops it from the theme picker on a CP user |
| `web/client/form/client.tform.php` | `ispconfig_version` | drops it from the client theme picker |
| `web/client/form/reseller.tform.php` | `ispconfig_version` | drops it from the reseller theme picker |
| `web/tools/form/tpl_default.tform.php` | `ISPC_VERSION` | drops it from *Tools → Default user settings* |
| `web/client/form/client_circle.tform.php` | `ISPC_VERSION` | drops it from the client-circle theme picker |

The two filenames do not behave the same way when the file is *absent*. `login/index.php` requires `ispconfig_version` to exist and match, so a theme without it is rejected at login. The other five `ispconfig_version` sites treat a missing file as "not gated". Both `ISPC_VERSION` sites require a present, matching file. The practical consequence is the same either way: run `install.sh`, which stamps both files, rather than reasoning about which screen tolerates what.

Skip the re-stamp and the failure is quiet. Every user lands on a stock-looking panel, and the design disappears from the Design drop-down so it cannot simply be re-selected. Nothing in the panel says the theme is out of date by one patch level. The recovery is cheap: core changes only the **session**, never the stored `sys_user.app_theme` column, so re-running `install.sh` and logging back in brings it straight back, with no database repair.

If the installer cannot find `ISPC_APP_VERSION` in your config it removes any stale stamp rather than leaving a wrong one in place, prints a warning, and gives you the two `printf` commands to write the files by hand. A stamp from a previous panel version is worse than no stamp: it makes the design look selectable and then resets everyone at login.

### The Branding page needs no re-stamp

The version gate applies to design directories only. Two things are still worth checking after an upgrade:

- If an upgrade ever did remove `interface/web/customizer`, re-run `./install.sh --module`.
- Module assignment is per user, so admin accounts created *after* the install do not have it. Re-run `./install.sh --module`, or tick `customizer` under *System → CP Users → edit the user → Modules*.

## Checking the templates

Overriding works because ISPConfig's template engine searches `themes/<theme>/templates` before falling back to `themes/default/templates` (`interface/lib/classes/tpl_ini.inc.php`), with a module-scoped lookup at `themes/<theme>/templates/<module>/<file>` taking priority over both (`tpl.inc.php`, `_fileSearch`). Any template a design does not provide falls through to stock.

### clarity: seven overrides, checked by hand

| Override | Replaces |
|---|---|
| `templates/main.tpl.htm` | the app frame |
| `templates/main_login.tpl.htm` | the login scene |
| `templates/topnav.tpl.htm` | the module navigation |
| `templates/dashboard/dashboard.htm` | `web/dashboard/templates/dashboard.htm` |
| `templates/dashboard/modules.htm` | `web/dashboard/dashlets/templates/modules.htm` |
| `templates/dashboard/metrics.htm` | `web/dashboard/dashlets/templates/metrics.htm` |
| `templates/dashboard/donate.htm` | `web/dashboard/dashlets/templates/donate.htm` |

`themes/clarity/BUILT-AGAINST.txt` pins all seven against the exact stock contract each one consumes: template variables, loop names, the `data-capp` click contract on the module tiles, the four canvas ids the metrics charts key on, and the JS hooks the stock shell scripts (`pushy.js`, `ispconfig.js`, `responsive.js`) expect in the frame. It records that these were verified against ISPConfig 3.3.1p1.

A changed stock template raises no error; it renders an override whose variables no longer resolve, so a dashlet comes up empty or stale. Patch releases have not changed these in practice; a major release can. After a major upgrade, diff the new stock templates against the overrides:

```bash
cd /usr/local/ispconfig/interface/web
diff themes/default/templates/main.tpl.htm       themes/clarity/templates/main.tpl.htm
diff themes/default/templates/main_login.tpl.htm themes/clarity/templates/main_login.tpl.htm
diff themes/default/templates/topnav.tpl.htm     themes/clarity/templates/topnav.tpl.htm
diff dashboard/templates/dashboard.htm           themes/clarity/templates/dashboard/dashboard.htm
diff dashboard/dashlets/templates/modules.htm    themes/clarity/templates/dashboard/modules.htm
diff dashboard/dashlets/templates/metrics.htm    themes/clarity/templates/dashboard/metrics.htm
diff dashboard/dashlets/templates/donate.htm     themes/clarity/templates/dashboard/donate.htm
```

These overrides are full rewrites, so the diffs are large; a clean diff is not the goal. What matters is any `{tmpl_var name='...'}` or `{tmpl_loop name='...'}` present in the new stock file and missing from the override, and any change to the ids and `data-` attributes listed in `BUILT-AGAINST.txt`. For a cleaner signal, diff stock against stock: unpack the ISPConfig source tarball for the version you upgraded *from* and diff its copy of each template against the one now installed.

If a contract did change, fix the override and update the pin in `BUILT-AGAINST.txt`. CI checks that every override is *documented*; it cannot know a future stock template changed, so this check is manual. As a fallback, deleting `themes/clarity/templates/dashboard/` restores the stock dashlets, which still pick up the design's CSS. The three shell templates cannot be dropped this way.

### classic: two templates, regenerated on every install run

classic ships `brand.php`, `title.php`, `favicon.php` and a README, and no templates. Its two shells are generated at install time from the target panel's own `themes/default/templates/`, by four mechanical changes: asset paths pinned to `themes/default/assets/`; `brand.php`, `title.php` and `favicon.php` linked immediately before `</head>`; stock's `<link rel='icon'>` and `rel='shortcut icon'` tags replaced by that one `favicon.php` link; and, in the app frame only, the stock footer credit split into two spans so each credit toggle has a target. The installer then verifies the output — length against the source (counting the icon links it replaced, so the check tracks the transform rather than a constant), no surviving `current_theme` reference, all three brand endpoints present, exactly one tab-icon link and it is the right one — and refuses to deploy a shell it cannot account for.

So there is no manual diff for classic. Re-running `install.sh`, which the version stamp already requires, replaces `templates/` wholesale with a shell built from the new stock markup. Two outcomes are worth knowing:

- If the new stock shell is not a shape the generator recognises, `install.sh` prints the reason and exits **before** classic is deployed. The design half runs first, so with `--design=all` clarity is installed and survives, while the Branding page does not get installed. Fall back to clarity and report your ISPConfig version.
- If only the footer credit line cannot be found, that is a warning rather than an error: everything installs and works, and the two credit toggles have no effect on classic until the generator is taught the new markup.

With a symlink install the generated templates are written *through* the link, into `themes/classic/templates/` in your clone. They are gitignored, and every install run replaces them wholesale.

## Re-applying the web-server snippet

The version-gate files sit inside the panel's web root, so the web server serves them as ordinary static files, and an unauthenticated `200` there returns your exact ISPConfig version and patch level. `contrib/webserver/` carries nginx and Apache snippets and the full explanation; they match any theme directory rather than a named one, so a single rule covers both designs.

The ISPConfig updater can regenerate the panel vhost when you let it reconfigure services, which drops the snippet. Re-check it after an upgrade, at the same time you re-stamp:

```bash
for d in clarity classic; do
  curl -sk -o /dev/null -w "$d %{http_code}\n" \
    https://panel.example.com:8080/themes/$d/ispconfig_version
done
```

`403` or `404` means the rule is live — though a design you did not install returns 404 either way, so read the installed ones. `200` means the rule is gone: re-apply the snippet and reload the web server. The deny rule only affects HTTP requests; ISPConfig reads those files from disk, so the design keeps working. If the design *does* revert after you apply the snippet, the stamp is missing or stale, which is the re-stamp above rather than the snippet.

## Upgrading this extension

```bash
cd /opt/ispconfig-theme-customizer
git fetch --tags
git checkout <tag>
sudo ./install.sh                       # add --copy / --design as you installed
```

There is no in-panel upgrade path. *System → Extension Installer* lists only the repository ISPConfig UG curates, so this extension is installed and upgraded by cloning it and running `install.sh`.

With a symlink install the panel reads the design from the clone, so a tag checkout is live immediately — re-run `install.sh` anyway. It re-stamps the gate, regenerates classic's shell if classic is in the run, and re-runs module assignment; for a `--copy` install it is the step that deploys the new files at all. Hard-refresh the browser (`Ctrl+Shift+R`) so the new CSS is picked up.

No release listed below has a migration step, a schema change or a new column. Everything the Branding page stores lives in the same `sys_ini` row throughout.

### v3.1.0

**If you installed before v3.1.0 with the default (symlink) mode, re-running `./install.sh` is the whole remedy.** Before v3.1.0 every branding endpoint located the panel with a path built from `__DIR__`, which PHP resolves through symlinks. Since `install.sh` defaults to symlink mode, that path landed in the git clone rather than the panel, `config.inc.php` was never found, and the endpoints took their database-failure path: a valid but empty response. The visible symptom was that branding appeared to do nothing, with no error, no log entry and no 404 to chase. Panels installed with `--copy` were unaffected. Nothing in the database changed, so the stored branding comes back as it was.

This is also the release that added the `classic` design and the two logo variants. A panel with only the historical `custom_logo` renders exactly as it did, because each surface falls back to the other variant when its own is unset.

### v3.1.1 and v3.1.2

Per-surface logo-variant preference (`logo_variant_nav`, `logo_variant_login`) and its bug fixes. Both keys are unset by default, which means Automatic, so nothing changes on an existing panel until you set one.

### v3.2.0

Adds the donation-dashlet switch, default on. Switching it off writes the same `sys_config` row ISPConfig's own **Hide** button writes. On a panel whose admin has never clicked that button the row does not exist yet, so the first save creates it; `bin/purge_branding.php` deletes it again, but only where the stored value is one this module can have written.

### v3.3.0

Adds the `show_design_picker` key, which hides the Design drop-down under *Tools → User Settings*. If you maintain your own design, add it to that design's `brand.php`: CI's **Brand-token contract parity** step walks every `themes/*/brand.php` and requires it.

### v3.4.0

Adds `rail_hex_light`, the sidebar colour in light colour mode, and the `preview.php` endpoint behind the Branding page's live preview. **Nothing changes on an existing panel until you set `rail_hex_light`:** unset, every design keeps painting the sidebar from `rail_hex` in both modes. Downgrading is equally uneventful — an older design's `brand.php` does not read the key, so it is ignored and the value stays in the config blob. If you maintain your own design, add `rail_hex_light` to its `brand.php`: paint your light scope's rail with it where you have one, or read it and document the no-op where you do not.

This release also retires six wordbook keys. `logo_head_txt`, `brand_head_txt` and `credits_head_txt` are gone, replaced by five new legend headings (`identity_head_txt`, `placement_head_txt`, `colour_head_txt`, `preview_head_txt`, `visibility_head_txt`); `used_logo_txt`, `used_logo_on_dark_txt` and `used_favicon_txt` labelled the "Current logo" and "Current favicon" rows the inline upload blocks replaced. There is no compatibility shim, because a wordbook key with nothing left to label has nothing to fall back to.

### v3.4.1

Live-defect fixes on the redesigned Branding page. No key changes, no action.

### v3.5.0

A design pass over the Branding page: it is now built around its own preview, with a full-width strip at the top carrying the two supplied marks, the panel name, three status facts and the colour chips in a legend, and the settings in five cards under that. What it stores is unchanged — same keys, same `sys_ini` row, same `sys_config` row for the donation switch.

- **The page heading now reads "Branding."** `page_head_txt` held "Customizer" while the navigation item beside it already said "Branding". Only the heading text changed, in all seven shipped locales; the module is still `customizer` and its URL is unchanged.
- **The six visibility switches were relabelled.** "Show the software version" is now "Software version", and so on: a switch already says "show". The settings and their keys are unchanged.
- **Twenty-three wordbook keys were added**, seventeen to the form wordbook (`lib/lang/<lang>_customizer.lng`) and six to the module wordbook (`lib/lang/<lang>.lng`, where the preview endpoint can reach them). If you maintain a translation of your own, add all twenty-three: ISPConfig *substitutes* wordbooks rather than merging them, so a file that exists but omits a key renders the raw key name in the UI. `.github/scripts/lang_check.php` lists exactly what is missing.
- **Three form-wordbook keys were retired**: `rail_contrast_txt`, `preview_nav_txt` and `logo_removed_txt`. The new layout's status facts and measured-ratio captions replaced what the first two labelled, and the third labelled a standalone confirmation the inline drop-zone line replaced. A third-party translation carrying them keeps them harmlessly.
- **No design has to change.** The page's stylesheet is inline and reads design tokens through the same `var(--pz-…, var(--nz-…, …))` chains it always did, and the brand-token contract is untouched.

## Upgrading from the old split installation

Only relevant if you installed before v3.0.0. Until then this shipped as two repositories — `clarity-theme-ispconfig` and `ispconfig-customizer` — with independent version numbers, and nothing enforced that the halves matched: `themes/clarity/brand.php` reads exactly the `sys_ini` keys `customizer_edit.php` writes, so the module at v1.0.12 against the theme at v2.1.0 left the accent colour silently unapplied, with no error anywhere. That is why they merged. It is one extension now, with one version number and one tag, and CI enforces the contract.

There is no migration to perform. The branding data is untouched — it was always in ISPConfig's own `sys_ini` row, never in either repository — and `install.sh` deploys to the same two destinations the old installers did.

```bash
cd /opt
git clone https://github.com/wadejbeckett/ispconfig-theme-customizer.git
cd ispconfig-theme-customizer
sudo ./install.sh                       # add --copy if that is how you had it
```

A bare run installs clarity, which is what the old split installation was. Then log out and back in, confirm the design renders, and confirm *Branding* still shows your logo, colours and panel name.

Once verified, **remove the old clones**, typically at `/root/clarity-theme` and `/root/ispconfig-customizer`. `install.sh` looks for those two paths (plus `/opt/clarity-theme-ispconfig` and `/opt/ispconfig-customizer`) and prints a note if it finds one, but it will not delete anything outside its own destinations. The risk is concrete: those clones still contain working installers that deploy older code to the same destinations, so anyone who runs one afterwards — or any cron job still referencing them — silently overwrites this install with pre-merge code.

```bash
rm -rf /root/clarity-theme /root/ispconfig-customizer
```

Two related notes. **There are no submodules**: the old `ispconfig-toolkit` umbrella repository pinned those two as git submodules and is archived read-only, so do not clone this one with `--recurse-submodules`. And if the old theme install was a symlink, `ispconfig_version` and `ISPC_VERSION` were written *through* the link into the old clone; deleting the clone removes them, and the new install writes its own.

## Uninstalling

`uninstall.sh` does not restore stock by default. Nothing it does edits an ISPConfig core file or configuration.

```
./uninstall.sh [--theme|--module|--all] [--design=<name>] [--reset-users]
               [--purge-branding] [--keep-assignment] [ISPCONFIG_ROOT]
```

| What | Default | Flag |
|---|---|---|
| Remove the design directories | yes, **all** designs | `--design=<name>` to narrow |
| Reset `sys_user.app_theme` from the removed designs to `default` | **no** | `--reset-users` |
| Revert `$conf['theme']` | **never** — manual, in both files | — |
| Remove `interface/web/customizer` | yes | — |
| Strip `customizer` from users' module lists, repointing any `startmodule` that pointed at it | yes | `--keep-assignment` to skip |
| Wipe stored branding values | **no** | `--purge-branding` |

`--design` is the same separate axis it is in `install.sh`, with the opposite default of **all designs**: installing picks what you want, uninstalling has to clear whatever might be there, and removing a design that was never installed only prints "already removed".

On a symlink install, removing a design also clears what was written *through* the link into your clone: both version stamps, and for classic the generated `templates/`. Left behind, they would be inherited by a later install against a different panel.

The two defaults that catch people out:

**`sys_user.app_theme` is left alone unless you pass `--reset-users`.** Core falls back to the default theme at session level only; it never heals the stored column. Leave rows pointing at a design whose directory is gone and every affected user gets a "theme not compatible" banner at *every* login. The default exists so a reinstall keeps everyone's selection. It resets exactly the designs being removed, so narrowing with `--design` narrows the reset too.

**Branding values are preserved unless you pass `--purge-branding`.** They are ISPConfig's own fields: the panel name, login text and logo keep rendering on the stock theme because core reads `sys_ini.custom_logo` and the `[misc]` keys itself, and they stay editable under *System → Interface Config*. The `[branding]` section sits inert for any brand-aware design.

`bin/purge_branding.php` restores the three core-owned `dashboard_atom_url_*` keys before dropping `[branding]`, but only where the stash recorded a URL *and* the live key is still empty — a key holding a URL again has been set by hand since, and is never overwritten. Where nothing was stashed, it does not guess a URL back in: it reports which roles are left with the feed off, and the stock URL to paste under *System → Interface Config*. It blanks rather than deletes the three stock `[misc]` keys, because those are real fields of that screen.

**Reverting `$conf['theme']` is always yours to do.** If you set it to `'clarity'` or `'classic'`, set it back to `'default'` in **both** `interface/lib/config.inc.php` and `server/lib/config.inc.php`. The uninstaller checks for the line and warns *before* it removes anything, because the failure mode is ugly: core falls back to the stock login template, which resolves its stylesheets and scripts against the directory of the design that is now gone, so every one of them 404s. Login still works; the page is unstyled and no error is shown.

Both `bin/reset_app_theme.php` and `bin/purge_branding.php` are idempotent and can be run directly, which is what you want if the database was unreachable during the uninstall:

```bash
php bin/reset_app_theme.php /usr/local/ispconfig/interface/lib/config.inc.php
php bin/purge_branding.php  /usr/local/ispconfig/interface/lib/config.inc.php
```

`reset_app_theme.php` takes design names after the config path and resets every design this repository ships when given none.

## Version support

Developed and verified against **ISPConfig 3.3.1p1**. That is the version clarity's seven template overrides are pinned to in `themes/clarity/BUILT-AGAINST.txt`, and the version the core behaviour described above was read from. classic pins nothing, because it has nothing to pin: its shell is built from whatever panel it is installed on. It does assume the shape of the stock shell, and fails loudly rather than quietly when that shape is not one it recognises. ISPConfig 3.2 has not been tested — neither claimed as supported nor known to be broken.
